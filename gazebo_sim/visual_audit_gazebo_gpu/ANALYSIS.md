## 训练链路需要核对的具体问题

根据微调 manifest：batch_size=16，epochs=4，load_epoch=30，stop_epoch=33，
goal_mask_prob=0.5，alpha=1e-4，eval_freq=999。

1. 当前仓库 `train_eval_loop_nomad` 每个训练 epoch 调用两次 scheduler.step()。
   `train.py` 的指定 epoch 恢复代码也明确按 2 倍 epoch 数推进调度器。
   这是实际代码行为，与标准每 epoch 一步的时间尺度不同。
   修复时必须同时核对恢复逻辑和调度器 checkpoint 的保存时刻，不能只删除一处就声称恢复一致。
   尚无这次微调的训练日志/源码版本证明它实际执行的完整学习率序列。
2. 按当前源码，load_epoch=30 后从 epoch 31 运行到 stop_epoch=33，共 3 个 epoch，
   不是单看 epochs=4 就能断定训练了 4 个 epoch。需要日志核实。
3. eval_freq=999 在上述短训练期间不会触发验证，无法依据验证结果选模型。
4. 库内 00–05 的轨迹，按 context=3、horizon=8、spacing=1 计算共 188 个候选观测点，
   batch 16 约 12 个 batch/epoch。goals_per_obs=2 在当前 `_build_index` 中没有重复观测点。
   这是库内文件的估算，不等于已验证本地训练时的 dataset 长度。
5. 按库内轨迹第 3 个未来点的机体坐标方向统计，188 个候选中，
   左转超过 15° 的为 23 个，右转超过 15° 的为 16 个，其余主要接近直行。
   这还是动作 mask、随机目标和 50% goal masking 之前的候选数。
